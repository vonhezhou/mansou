# 漫搜 · Mansou 执行计划

> 本文保留早期阶段规划，不是当前功能清单或交付承诺。产品范围以 [README](../README.md) 为准，实现以当前前后端架构文档为准。

## 1. 项目阶段

整体按 6 个阶段推进。前 3 个阶段目标是从 PoC 变成可持续开发的正式项目骨架；后 3 个阶段完善产品能力、稳定性和部署。

## 2. 阶段 0：项目初始化

目标：建立 `mansou` 正式仓库结构，并让 PoC 能在新项目中继续运行。

任务：

- 初始化 pnpm workspace、TypeScript、ESLint/Prettier、Vitest。
- 建立 `apps/server`、`apps/web`、`packages/contracts`、`packages/plugin-runtime`、`packages/core`、`packages/storage`、`packages/shared` 目录。
- 从 `venera_web_poc` 迁移 Fastify 服务、运行时、下载、图片代理、配置、fixtures。
- 保留 PoC 的 mock 源和最小 API，确保迁移后 `pnpm dev`、`pnpm build`、`pnpm test` 可运行。
- 增加 `.env.example`、`README.md`、`doc` 文档入口。

验收标准：

- 新项目能启动服务并访问健康检查。
- mock 源搜索、详情、章节、图片代理可用。
- 构建和类型检查通过。

建议周期：2 到 3 天。

## 3. 阶段 1：后端分层与 API 正式化

目标：拆分 PoC 的单体 `server.ts`，形成可维护后端结构和稳定 API 契约。

任务：

- 建立 `/api/v1` 路由命名空间。
- 将源仓库、源管理、搜索、漫画详情、图片、下载、调试路由拆分到独立 route modules。
- 在 `packages/contracts` 定义核心 Zod schema 和 TypeScript 类型。
- 实现统一错误格式、`requestId`、全局错误处理和输入校验。
- 生成或维护 OpenAPI 文档。
- 为 mock 源主路径增加 API 集成测试。

验收标准：

- 所有 PoC API 主能力在 `/api/v1` 下可用。
- 错误响应统一，插件异常不会泄漏不必要的内部信息。
- API schema 可被前端复用。

建议周期：4 到 6 天。

## 4. 阶段 2：存储正式化

目标：用 SQLite 管理结构化状态，保留文件系统存储大文件和脚本。

任务：

- 选型 SQLite 访问层，建议 Drizzle ORM 或 Kysely，也可先用轻量 SQL 封装。
- 设计并实现数据库迁移机制。
- 建立 `sources`、`source_settings`、`plugin_data`、`favorites`、`downloads`、`download_items`、`cache_entries`、`app_settings` 表。
- 将 PoC 的 `SourceDataStore`、Cookie Store、下载任务 JSON 持久化迁移到 storage 层。
- 编写旧 JSON 数据导入脚本，允许从 PoC `data` 目录迁移。
- 增加备份和恢复命令的基础实现。

验收标准：

- 重启后源、设置、Cookie、下载任务状态可恢复。
- 并发更新下载任务时不会破坏任务文件或数据库状态。
- 数据库迁移可重复执行且可在空数据目录初始化。

建议周期：5 到 8 天。

## 5. 阶段 3：插件运行时兼容性增强

目标：将运行时从“能跑部分源”提升到“可系统性兼容 Venera 插件”。

任务：

- 建立 Venera JS API 兼容清单，对照 `venera/doc/js_api.md` 和 `venera/doc/comic_source.md`。
- 补齐 `Network.fetchBytes`、`sendRequest`、`put`、`delete`、`patch` 和二进制响应。
- 补齐 `Convert.sha512`、`hmac`、AES CBC/CFB/OFB、必要 RSA 能力。
- 完善 `HtmlDocument`、`HtmlElement` 的 DOM 兼容行为。
- 规范插件实例生命周期：加载、初始化、重载、卸载、启停、能力探测。
- 增加插件调用超时、并发限制、错误分类和调试摘要。
- 建立真实源兼容矩阵，至少选择 3 到 5 个代表性源验证。
- 评估 `isolated-vm`、Worker Thread、子进程隔离方案，并给出是否替换 Node `vm` 的结论。

验收标准：

- mock 源和选定真实源的搜索、详情、章节、图片主路径通过。
- 每个兼容失败都有明确缺失 API 或网络/登录原因记录。
- 运行时 API 有单元测试覆盖。

建议周期：8 到 12 天。

## 6. 阶段 4：正式 Web 前端

目标：替换 PoC 最小 UI，提供可日常使用的 Web 漫画阅读体验。

任务：

- 初始化 `apps/web`，建议使用 React + Vite + TypeScript。
- 接入 contracts 类型和请求客户端。
- 实现基础布局、路由、错误页、加载状态和移动端适配。
- 实现源管理：可用源列表、安装、更新、启停、设置、Cookie 导入。
- 实现搜索：聚合搜索、源筛选、搜索选项、部分失败展示。
- 实现详情页：封面、元信息、标签、章节、缩略图、推荐入口。
- 实现阅读器：长条模式、分页模式预留、图片预加载、进度保存、键盘/触摸操作。
- 实现下载页：任务列表、状态、日志、取消、重试、导出 CBZ。
- 实现设置页：代理、并发、缓存、调试开关、数据目录信息。

验收标准：

- 用户能通过 Web 完成安装源、搜索、打开详情、阅读、下载的完整流程。
- 桌面和移动端基础布局可用。
- 前端对 API 错误、源失败、图片加载失败有明确提示。

建议周期：10 到 15 天。

## 7. 阶段 5：下载、缓存与阅读体验增强

目标：让核心阅读和离线能力达到正式应用可用标准。

任务：

- 下载任务改为基于数据库的可靠队列。
- 支持下载断点续传和失败图片单独重试。
- 增加下载任务 SSE/WebSocket 推送，减少轮询。
- 完善图片缓存策略：最大容量、LRU 清理、手动清理、缓存统计。
- 阅读器增加预加载窗口、失败重试、缩放、适应宽度、阅读方向设置。
- 支持本地下载库浏览和从下载文件阅读。

验收标准：

- 服务重启后下载任务可以恢复到可理解状态，并能重试未完成任务。
- 图片缓存不会无限增长。
- 章节预览不记录阅读历史；旧数据库中的历史数据保留，新数据库不再创建历史表。

建议周期：8 到 12 天。

## 8. 阶段 6：部署、安全与发布

目标：完成正式项目的交付闭环。

任务：

- 编写 Dockerfile 和 docker-compose 示例。
- 支持数据目录挂载、环境变量配置、健康检查。
- 增加反向代理部署说明。
- 增加基础认证或访问 token，至少保护非本地部署场景。
- 限制图片代理 SSRF 风险：协议白名单、可选域名策略、响应大小限制。
- 插件安装记录来源 URL、版本、hash。
- 增加日志文件轮转或结构化日志输出配置。
- 建立 CI：类型检查、lint、测试、构建、Docker 构建。
- 编写用户文档：安装、源管理、代理、Cookie、下载、常见问题。

验收标准：

- 用户可通过 Docker 在 NAS 或 Linux 服务器部署。
- CI 覆盖主要质量门禁。
- 发布包包含 README、配置示例和迁移说明。

建议周期：5 到 8 天。

## 9. 优先级清单

P0：

- 项目结构初始化。
- PoC 功能迁移并保持可运行。
- `/api/v1` 契约和统一错误处理。
- mock 源集成测试。
- 源安装、搜索、详情、章节、图片代理主路径。

P1：

- SQLite 持久化。
- 正式 Web 前端主流程。
- 下载任务可靠化。
- 插件 API 兼容清单和真实源矩阵。
- Docker 部署。

P2：

- WebView 登录替代方案。
- 评论、评分、收藏同步等高级源能力。
- 多用户认证。
- PWA/桌面壳。
- 更强插件沙箱。

## 10. 风险与应对

插件运行时安全风险：

- 风险：第三方插件可执行任意 JS，Node `vm` 不是强安全沙箱。
- 应对：封装 RuntimeAdapter，限制全局对象，禁用 Node 模块访问；中期评估 Worker/子进程/isolated-vm。

真实源反爬和登录风险：

- 风险：部分源依赖 Cloudflare、WebView、人机验证或复杂 Cookie。
- 应对：保留 Cookie 导入，提供调试 API；设计 Web 端登录/验证交互协议；兼容矩阵中标记限制。

插件 API 不完整风险：

- 风险：PoC 只实现常用 API 子集，真实源会不断暴露缺口。
- 应对：按真实源错误补齐兼容层，并为每个缺口增加测试。

下载可靠性风险：

- 风险：进程退出、网络失败、文件写入失败会导致任务状态不一致。
- 应对：下载明细持久化、幂等写入、失败重试、启动时任务恢复扫描。

数据迁移风险：

- 风险：从 JSON 文件迁移到 SQLite 后损坏用户数据。
- 应对：迁移前自动备份旧 data；迁移脚本可重复执行；保留只读导入模式。

## 11. 建议首个迭代切片

第一个迭代建议只做“正式骨架 + PoC 能力迁移”，避免一开始同时重写前端和存储。

范围：

- 建立 monorepo。
- 迁移 PoC server 到 `apps/server`。
- 抽出 contracts 中的 `Comic`、`ComicDetails`、`SourceSummary`、`DownloadTask`。
- 保留文件存储。
- 路由升级到 `/api/v1`。
- 加入 mock 源集成测试。

不做：

- 不立即替换为 SQLite。
- 不立即实现完整 Web 前端。
- 不立即替换 Node `vm`。
- 不立即支持多用户。

完成后再进入第二迭代，分别推进 SQLite 和 Web 前端主流程。
